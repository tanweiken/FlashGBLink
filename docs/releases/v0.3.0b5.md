**Reverts the `0.3.0b3` / `0.3.0b4` timing changes. This is `0.3.0b2`'s
configuration — the fastest one measured — with the CRC32 payload and everything
learned since written down.** Plugin `0.3.0b5`; `main` stays on 0.2.3.

The SO ready-line handshake stays exactly as `0.3.0b1` shipped it: tight 2 µs
arm / 5 µs settle margins, 1.25 Mbaud, and a word that costs about 43 µs instead
of the fixed 150 µs. `0.3.0b3` widened the margins so the handshake also held at
1.8 Mbaud, and `0.3.0b4` made 1.8 Mbaud the default. Both were slower on real
hardware, and `0.3.0b5` goes back.

## Why b3/b4 were reverted

| Build | Margins | Clock | Throughput (FlashGBX) |
|---|---|---|---|
| `0.3.0b2` | 2 µs / 5 µs | 1.25 Mbaud | **42–45 KiB/s** |
| `0.3.0b4` | 5 µs / 20 µs | 1.8 Mbaud | 39–40 KiB/s |

The settle is paid per word, and at this link the clock is a minority of each
word's time: 1.8 Mbaud returns about 6 µs of the ~13 µs the wider margins cost.
The CLI microbenchmark in `0.3.0b4`'s notes showed 4 MiB reads at 52 s (1.8
Mbaud) against 58 s (1.25 Mbaud) *within the wide-margin firmware* — it never
compared against the tight 2 µs / 5 µs build, which does the same read in 45 s.

## What each build was

| Build | Firmware | Margins | Default clock |
|---|---|---|---|
| `0.3.0b2` | `a1257e4` | 2 µs / 5 µs | 1.25 Mbaud |
| `0.3.0b3` | `b68a37d` | 5 µs / 20 µs | 1.25 Mbaud |
| `0.3.0b4` | `b68a37d` | 5 µs / 20 µs | 1.8 Mbaud |
| **`0.3.0b5`** | **`a1257e4`** | **2 µs / 5 µs** | **1.25 Mbaud** |

The payload, plugin code and CLI are unchanged from `0.3.0b2`/`0.3.0b4` apart
from the plugin version string and the documentation.

## Install

1. **Pico**: flash `gbasend-pico.uf2` below (or `-rgb` for a WS2812 on GP16).
   These are the tight-margin `a1257e4` images — a Pico running `0.3.0b3` or
   `0.3.0b4` firmware must be reflashed to get the speed back.
2. **Plugin**: extract `FlashGBLink-plugin.zip` below into FlashGBX's
   `plugins/` directory.
3. **gbasend**: build from <https://github.com/tanweiken/gbasend-rs>; the CLI is
   an uploader only and runs the multiboot at 256 kHz, where the margins are not
   used, so either `a1257e4` or the fork's newer `b68a37d` works.

## If you need more than 1.25 Mbaud

Build the fork at `b68a37d` and flash its wide-margin images: the handshake then
holds to 1.8 Mbaud (1.9 mismatches on the test hardware). Expect it to be slower
than this release at 1.25 Mbaud. The choice is documented in
`firmware/README.md`.

## Confirmed on hardware

After reflashing the tight images, `0.3.0b5` measured **45 KiB/s** through
FlashGBX, matching `0.3.0b2`. An earlier 37 KiB/s reading came from this plugin
running against a Pico still carrying the `b68a37d` wide-margin images, so the
pairing is practical, not cosmetic:

| Firmware | Clock | Throughput, FlashGBX |
|---|---|---|
| tight `a1257e4` (this release) | 1.25 Mbaud | 42–45 KiB/s |
| wide `b68a37d` | 1.25 Mbaud | ~37 KiB/s |
| wide `b68a37d` | 1.8 Mbaud | 39–40 KiB/s |

If throughput looks low after upgrading, check the Pico's image before anything
else.

## Compatibility

- `main` (0.2.3) and upstream `gbasend` are unaffected; do not mix a payload
  from one line with firmware from the other.
- The handshake only engages at or above 1 Mbaud. The BIOS multiboot upload
  (256 kHz), a session below 1 Mbaud and an older payload all keep the fixed
  delay, so mixed installs stay safe but get no speedup.
- Validated on the 32 MiB M36 cartridge only; other profiles are not yet
  tested.
